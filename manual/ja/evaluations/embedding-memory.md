# 「おまかせで整える」でデスクトップアプリが 11 GB 使ったのはなぜか <Badge type="info" text="2026-11-05 測定 · v0.120" />

**確かめたこと。** 約 2,300 ページのナレッジで **おまかせで整える** を走らせると、デスクトップアプリの本体プロセスが数分で 11〜12 GB に膨らみ（起きた Mac からの報告値）、Mac 全体がスワップ（メモリがあふれてディスクを使うこと）に入りました。メモリを抱えていたのは、Web ビューでも AI サーバーでもなく、ネイティブの本体です。何がメモリを持っていたのか、どう止めるのかを調べました。

**ひとことで。** 原因は、端末内の埋め込みエンジンでした。直し方は、依存ライブラリの版を固定することと、1 回に渡す文の数を減らすことです。あなたの側の設定は何も変わりません。

- `fastembed` 7.5 が同梱する ONNX Runtime（1.31）では、32 節のページ 1 枚を埋め込むだけで、この Mac の本体が 39 GB を超え、終わりませんでした。
- ONNX Runtime 1.23 を同梱する `fastembed` 5.13 では、同じ呼び出しが 6.5 秒で終わりました。大きな確保のピークは 1.4 GB です。600 MB のモデルを載せた状態で、プロセス全体は約 2.4 GB でした。

## 測り方

| | |
|---|---|
| 機材 | M1 Max（10 コア・64 GB）、macOS 26 |
| ビルド | デスクトップアプリの debug ビルドに、計測コードを足したもの。計測コードは、アプリが呼ぶのと同じネイティブ命令を、Web ビューからループで呼び続ける。データは隔離したフォルダで、実データには触れていません |
| 負荷 | **埋め込み:** 約 3,000 字の文 × 32（各 512 トークンで切られる。長い 32 節のページ 1 枚の改訂が送るものと同じ）、その 1 文だけ、300 字の短文 × 100。モデルは既定の `bge-m3` と `multilingual-e5-small`。**ファイル読み:** 最初に疑ったネイティブ命令で、10 MB のファイルを 180 回。13 MB の base64 文字列として 120 回、生のまま 60 回 |
| 記録 | プロセスの常駐メモリと `footprint` の `MALLOC_LARGE` 行を 3 秒ごと。常駐が 5〜8 GB を超えたら自動で止める見張り付き（見張りなしの最初の 1 回で、スワップを 25 GB 使ったため） |
| 版 | `fastembed` 7.5 は `ort` 2.0.0-rc.15（ONNX Runtime 1.31.0）に、`fastembed` 5.13.0 は `ort` 2.0.0-rc.11（1.23.2）に決まる。いずれも `Cargo.lock` で確認した。1.23.2 の文字列は、ビルドしたバイナリにもある。3 つ目のビルドの `fastembed` 5.8.0（1.22.0）は、1.23 と同じ挙動だった |

## 結果

**原因ではなかったもの。** ネイティブの橋を渡るファイル読みです。180 回読んでも、本体は 170〜260 MB のまま増えませんでした。

**原因だったもの。** 埋め込みエンジンと、それが同梱するランタイムです。

| 負荷 | ONNX Runtime 1.31（fastembed 7.5、前） | ONNX Runtime 1.23（fastembed 5.13、後） |
|---|---|---|
| bge-m3・32 節 × 512 トークン・1 回 | 40 秒たっても終わらない。大きな確保が 39 GB でまだ増えている（442 ブロック） | 6.5 秒。大きな確保のピークは 1 回 32 文で 3.2 GB、**1 回 8 文で 1.4 GB** |
| bge-m3・1 節だけ | 3 秒で常駐 5 GB、見張りが停止（arena 無効） | 1.23 では測り直していない（1.22 で 0.7〜1.0 秒） |
| e5-small・短文 100・1 回 8 文 | 6 秒で大きな確保が 4.3 GB、停止（arena 無効） | 2.7 秒・395 MB |

39 GB の行は、ランタイム既定のメモリ領域（arena）のままの結果です。1.31 の残り 2 行は、下の設定項目（knob）の試験からで、arena を切ったビルドで始めています。

1.31 で結果が**変わらなかった**こと（arena を切った実行の上に、それぞれ重ねて試しました）は、次のとおりです。

- 推論スレッドを 1 本にする。
- KleidiAI カーネルを切る。この Mac には SME がないので、もともと使われていなかった可能性が高いです。
- 重みの事前パックを切る。
- memory pattern を切る。

推論中のスタックを採ると、確保は ONNX Runtime 自身のノードごとの割り当て計画から来ていて、中身はふつうの中間テンソルでした。推論の中で再利用されない理由は、外からは見えませんでした。全部の層の中間テンソルの合計がピークになる、と考えると数字が合います。

1.23 でのバッチは、次のとおりです。

- 1 回 32 文と 1 回 8 文は、32 節で同じ 6.5 秒でした。
- 8 文のほうが、ピークは 3.2 GB から 1.4 GB に下がりました。
- アプリは 8 にしました。

## 分かったこと

- **2 つのビルドで変わったのは、同梱のランタイムです。** モデルファイル・トークナイザの設定・呼び出しは、`fastembed` 5.13 と 7.5 で同じです。もっとも近い上流の報告 microsoft/onnxruntime#29538 は、Apple Silicon で 1.24 以降に同じ形のメモリの保持が起きると述べています。この報告は、matmul 側の直しがないまま stale（更新がないこと）として閉じられています。この計測自体が比べたのは、1.22・1.23・1.31 だけです。Graphium は `fastembed` を 5.13.0 に固定しました。動かす前に繰り返す計測の手順も、リポジトリに残しています。
- **ピークは推論のあとも残ります。** 各実行のあと 8 秒の計測では、常駐メモリは下がりませんでした。ONNX Runtime の arena は自分では縮まりません。アプリは最後に使ってから 10 分でモデルを降ろすので、それまで約 2.4 GB が見える見込みです。10 分はアプリの決まりで、ここで測ったものではありません。
- **小さいバッチは損をしません。** 速さは同じで、ピークは半分以下になります。

## 限界

- 測ったのは、機材 1 台、macOS 1 版、条件ごとに 1 回です。上流の報告は Apple Silicon についてで、Windows はここでは測っていません。
- 負荷に使った文は、512 トークンの打ち切りに当てるための人工的なもの（語彙の繰り返し）です。実際のページはまちまちなので、表は 32 節のページの最悪値で、平均ではありません。
- 整える最中に、Web ビュー側が PDF の原文を読み直して使うメモリ（同じナレッジで 2〜4 GB）は、別の話です。今回は変えていません。
