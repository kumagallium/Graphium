# よくある質問

よく届く質問に答えるページです。特に、ナレッジ層について「なんでそうなったの？」と聞かれることが多いので、そこに正面から答えます。Graphium は、ここに出てくる数字をすべて、**自分で決めたコスト** か **手持ちのコーパスから実測した値** のどちらかにする方針です。隠れた品質フィルターは置きません。各質問をクリックすると、答えが開きます。

::: details 洞察があまり生成されないのはなぜ？

[洞察](/ja/knowledge-layer)は抽象化です。モデルが知見を読み、元の文脈の外でも通用する規則（「可搬性テスト」）を取り出そうとします。あまり出ないときは、次の順で確認してみてください。

1. **知見は収束していますか？** 一回きりの事実の寄せ集めには、抽出できる繰り返しのパターンがありません。モデルには、無理にひねり出すより空のリストを返すほうがよいと、はっきり指示してあります。そのため、コーパスがまだ育っていない間や、話題が散らばっている間は、0 件が正直な答えになることもあります。複数の知見が同じ規則の周りに集まりはじめると、洞察が生まれます。
2. **抽象化を担うモデルはどれですか？** 洞察の生成には、[設定](/ja/settings)の **モデルの割り当て** の **高度な処理のモデル** が使われます（未指定なら標準の処理のモデル、さらに軽い処理のモデルを使います）。抽象化は、パイプラインの中でいちばん難しいステップです。小さなローカルモデルは、強いモデルなら見つけるパターンでも、空のリストや知見の言い換えを返しがちです。ここには最上位級のモデル（例: Claude Opus / Claude Sonnet）をおすすめします。「推論対応」や大きさだけでは足りないことがあります。目安の表は [AI のセットアップ](/ja/ai-setup)にあります。

   洞察が少ないと感じたら、強いモデルを割り当てて、発見をもう一度実行してみてください。同じコーパスで、変わるのはモデルだけです。強いモデルでも何も出なければ、限界はソフトウェアではなく素材の側にあります。
3. **新しい洞察が増えず、既存の洞察に支持が足されていませんか？** 支持が足される道は 2 つあり、どちらも確かめを通ります。
    - (a) 既存の洞察を AI に見せます。知見が既存の洞察の規則の「もう 1 つの事例」なら、新しい洞察は書かず、その洞察を名指しします。足す前に、別の AI 呼び出しが、書かれているとおりの規則に本当に当てはまるかを確かめます。確かめられた知見だけが足されます。
    - (b) 新しい候補が既存の洞察と embedding で似ているときは、まだ「候補」にすぎません。同じ / 矛盾 / 別物を AI が判定して、同じものだけが支持追加になります。矛盾なら、両方の洞察をそのまま残して手入れタブに出します。

    どちらも結果パネルに *支持追加* として数えられます。支持追加が出ているなら、発見は機能しています。洞察が増える代わりに、手持ちの洞察が強くなっているだけです。
4. **本当に全部見終わっていますか？** スキャンは実測カバレッジを **視野 n/m 件** として報告します。これは、手持ちの知見のうち、少なくとも一度は AI が見た数です。取り込み時のスキャンには予算があるので（下の質問を参照）、大きなコーパスは、設計上、一度の取り込みでは一部しか見ません。全体をくまなく見たいときは、[設定](/ja/settings) → **ナレッジ管理** の **知見をまたぐ洞察を発見** を実行してください。実行前に、全件を視野に入れるのに必要な LLM 呼び出し回数の実測値が表示されます。終了後には、到達したカバレッジが報告されます。

:::

::: details Graphium がこっそり件数を制限していませんか？

していません。品質を理由に黙って捨てる処理はありません。モデルの確信度（confidence）は記録・表示されるだけで、候補の破棄には使われません。スキャンが作るべき件数の下限・上限もありません。知見も同じで、抽出する AI には「ノートが言えている点はすべて取り出す。固定の上限はない」と指示してあります。

知見は、ノートを開かなくても読めて、ノートが支える範囲を超えない形で書かせています。1 回の試行は 1 回の試行と分かる言い方にし、場面をまたぐ一般化は洞察に任せます（[この書かせ方を決めた測定](/ja/evaluations/claim-scope)）。

存在する数字は次の表のとおりで、それぞれ理由を確認できます。

| 数字 | 何か | なぜあるか |

| AI チャットに渡すナレッジの一覧はタイトルのみ・要約（旧種別）は載せない | 全ページを俯瞰する `<wiki-index>` の作り方 | **コンテキスト長の保護。** 各ページの本文プレビューまで載せると、大きな vault では入力が膨らみすぎます。一覧は全ページを漏らさず載せたままにします。プレビューにあたる内容は、検索で見つかった断片が別途文脈として渡ります |
| 検索結果の突き合わせに渡す候補 20 件 | 語彙検索と埋め込み検索の順位を 1 つにまとめるときの、候補の集まり | **組み立てコストを抑えるための上限です。** 検索そのものは両方とも全件を見ています。ここを絞っても取りこぼしは増えず、最終的に渡す断片は上の文字数の予算が決めます |
| 埋め込み検索に渡す質問文は 1000 字まで | 埋め込みモデルへの入力の切り詰め | **物理的な制約です。** multilingual-e5-large の入力上限は 512 トークンです。長い引用や貼り付けが混ざったときに検索ごと失敗しないよう、先頭を残して切ります |

| 既存の洞察への名指しの支持追加 | AI が「既存の洞察の規則のもう 1 つの事例」とした知見 | **しきい値はありません。** 類似度を入口にしません。<br>AI が洞察を名指しします。別の AI 呼び出しが、洞察の題・関係の形・本文と知見を照らして、1 件ずつ確かめます。<br>確かめられない知見は足しません（審査が失敗した・答えが無いときも足しません）。<br>洞察の本文は書き換えず、ゴミ箱・アーカイブの洞察には足しません。[測定の記録](/ja/evaluations/insight-reinforcement) |
| 重複判定のしきい値（embedding 類似度） | 既存の洞察との「一致候補」を絞り込む（最終判定ではない） | **これは候補探しで、判定ではありません。** embedding は否定や向きの違い（「下がる」と「上がる」）に鈍く、そのまま重複扱いにすると矛盾する洞察が支持として統合されてしまいます。<br>そこで、絞り込んだ候補のペアは、AI が同じ / 矛盾 / 別物を判定してから振り分けます。<br>同じなら支持追加にします。一致した洞察が、新しい裏づけの知見を得ます。<br>矛盾なら、両方の洞察をそのまま残し、手入れタブに `矛盾` として出します。両方を開いて見比べられます。<br>別物なら、新規ページにします。<br>embedding モデル未設定のときは、候補探し自体が素通りし、全部新規扱いです |

::: details Graphium とモデル、どちらの問題か切り分けるには？

対照実験を 1 つ回します。[設定](/ja/settings) → **ナレッジ管理** → **知見をまたぐ洞察を発見** を実行し、結果の行（*作成*・*支持追加*・*視野 n/m 件*）を控えてください。カバレッジが全件に達し、支持追加はあるのに新規がないなら、パイプラインは全部を見た上で「いまあるパターンは既存の洞察で説明済み」と判断しています。次に **高度な処理のモデル** に強いモデルを割り当てて、もう一度実行します。強いモデルでだけ洞察が生まれるなら、足を引っ張っていたのはモデルでした。それでも出なければ、知見にはまだ新しい繰り返しのパターンが育っていません。ノートを書き足して、収束を待つのが近道です。

:::

::: details 知見と洞察の違いは？

**知見**は、ノートや資料から取り出した命題 1 つです。**洞察**は、知見から取り出した、他の分野でも通じる関係の型です。細かく書かれたノートが知見で短い記述に絞られ、洞察でまた広い場面へつながります（ノート → 知見 → 洞察の、砂時計の形です）。全体像は[ナレッジ層](/ja/knowledge-layer)のページをどうぞ。

知見と洞察は Graphium 独自の拡張で、トピック（元の資料から直接作られ、常にオン）の上に乗っています。**設定 → AI** の、既定では折りたたまれている **先行公開の機能** にある **知見を使う** で丸ごとオフにできます（初めて使うときは既定オフ、以前から使っている場合はオン）。オフにすると、取り込み時の知見抽出が止まります（トピックの作成は、同じ資料テキストから引き続き動きます）。洞察は知見から作るので、洞察も一緒にオフになります。すでに作ったページは消えず、1 件でも残っていれば表示され続けます。

::: details Graphium でタスク管理やプロジェクト管理はできますか？

タスク管理ツールとしては使えません。これは機能が足りないからではなく、意図して引いた線です。Graphium は起きたことを記録する場所で、タスク管理ツールはこれから起きることを追いかける場所です。後者は期限・担当・優先度・進捗という「更新し続けなければならない状態」を持ちます。Graphium はそれを保存しません。更新が止まった状態は嘘になりますが、記録は一度本当であれば足りるからです。

その代わり、計画の「記録の側」は持っていて、それで足りることも多いはずです。

| したいこと | Graphium にあるもの |
|---|---|
| まだやっていないことを書き留める | ノートの中の**チェックリスト**（`/チェックリスト`）。項目ごとにチェックの有無の 1 ビットだけ |
| 会議の決定事項と TODO を見る | [音声ノート](/ja/voice-notes)の**要約**が、根拠の発言へのリンクつきで並べます |
| プロジェクトを計画して分解する | 「計画」フォルダのノート（**計画ノート**）と、行ごとのノートを持つ表。行ごとに工程ノートができ、予定の受け渡しは実績の横に点線で描かれます。[フォルダ](/ja/notes-and-editor#folders)を参照 |
| ノート横断でやり残しを見る | [MCP](/ja/mcp-server#やることとタスク管理ツール) でアシスタントに聞きます。`list_todos` が、まだチェックしていない項目をノートとブロックの ID つきで返します |

やらないこと: 項目に期限・担当・優先度を付ける、外からチェックを付ける、進捗のダッシュボードを描く。タスクを MCP の使えるツールで管理しているなら、両方を同じアシスタントにつないでください。「このノートのやり残しをタスクにして」は今日から使えますし、Graphium は相手がどのツールかを知る必要がありません。
